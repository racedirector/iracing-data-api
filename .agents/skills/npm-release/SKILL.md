# npm package releases

Use this repository's package-specific, tag-triggered release flow. Do not substitute a generic monorepo release process.

## Release contract

- Use `pnpm`; the root `package.json` pins pnpm 12.4.2.
- Treat only the `npm:` members of `dist-workspace.toml` as managed npm release targets. Resolve their paths to workspace `package.json` files dynamically. At the time this skill was authored they are `@iracing-data/oauth-schema`, `@iracing-data/oauth-client`, `@iracing-data/api-schema`, `@iracing-data/api-client-fetch`, and `@iracing-data/api-client-axios`; the file is authoritative if this list changes.
- Reject the root, examples, apps, other workspaces, `private: true` packages, packages without a version, and packages outside that managed set. A scoped name alone does not make a workspace releasable.
- Every managed package owns its version in its own `package.json`. Never use the root version or synchronize unrelated versions.
- Normal publication is performed by `.github/workflows/release.yml`, not locally. A pushed tag named `<full-package-name>@<version>` triggers it. There is no leading `v`.
- The workflow installs with `pnpm install --frozen-lockfile`, requires the tag version to equal the selected package's manifest version, builds `pnpm --filter "<package>..." --fail-if-no-match build`, and publishes only that package with public access.
- A version containing `-` is published under npm dist-tag `next`; a stable version is published under `latest`. The workflow does not infer `alpha`, `beta`, or `rc` differently.
- npm authentication is GitHub Actions trusted publishing/OIDC in the `npm` environment (`id-token: write`, empty token variables). Do not request a local npm login for the normal path.
- After a successful tag-triggered publish, the workflow creates a GitHub Release titled with the tag and generated notes. It does not pass `--prerelease`, so even npm prereleases are not marked as GitHub prereleases.
- `workflow_dispatch` is an operational fallback. It accepts an explicit package and either `latest` or `next`, skips tag/package-version matching, and does not create a GitHub Release. Do not use it for a normal release.

## Interpret the request

- A preview such as "what would be released" is read-only: discover, calculate, diff, validate what can be validated without mutation, and report a plan.
- "Prepare" means update the selected package manifests, run validation, and make the version-bump commit on the current feature/release branch. Do not tag, push a release tag, publish, or create a GitHub Release.
- "Release" or "publish", with unambiguous packages and versions, authorizes the complete established flow through pushing the release tag. Do not add a redundant confirmation. Still stop for an unsafe repository state, failed validation, a conflict, required review that is not complete, or a departure from this contract.

## Discover and resolve packages

1. Read `pnpm-workspace.yaml`, `dist-workspace.toml`, and the `package.json` at every `npm:` member. Do not copy versions from this skill.
2. For each candidate require:
   - it is a pnpm workspace;
   - its manifest name matches `@iracing-data/[a-z0-9][a-z0-9-]*`;
   - `private` is not `true`;
   - `version` is a valid SemVer string; and
   - its path is an `npm:` member of `dist-workspace.toml`.
3. Match user input in this order: exact full package name, exact unscoped suffix, then a unique case-insensitive substring among managed candidates. Ask only if no candidate or multiple candidates remain; never guess between `api-schema`, `oauth-schema`, or the two generated clients.
4. Read every selected manifest's current version immediately before calculating its target.
5. Read `dependencies`, `devDependencies`, `peerDependencies`, and `optionalDependencies` to build the selected packages' internal dependency graph. Publish selected dependencies before selected dependants.

The generated Axios and Fetch API clients use the same release flow. Their checked-in sources are generated by `pnpm codegen:client:api:axios` and `pnpm codegen:client:api:fetch`. Regenerate only when the change being released calls for it; the release workflow itself does not run code generation. Both generated packages also have a `prepare` build, but CI's explicit filtered build remains required.

## Determine versions

Accept an explicit valid SemVer or a `major`, `minor`, or `patch` intent. Calculate each package independently from its current manifest version.

- For a stable current version, use ordinary SemVer increments.
- For a prerelease current version, a stable `patch` intent promotes the same core (`X.Y.Z-alpha.N` to `X.Y.Z`); `minor` and `major` advance to their next stable cores.
- "next alpha" (and likewise `beta` or `rc`) increments the final numeric component only when the current version already has the same core and identifier, such as `0.0.1-alpha.8` to `0.0.1-alpha.9`.
- An explicit prerelease version is accepted if valid, greater than the current version, and unpublished.
- The repository has historical `alpha.N` and `beta.N` releases; the workflow accepts other valid identifiers and maps every prerelease to `next`. Do not invent how to choose a new prerelease base or switch identifiers. If the current version is stable, lacks a numeric prerelease suffix, or uses another identifier/core, ask for the intended explicit version or release line.
- Treat the word `next` as the npm dist-tag unless the user clearly describes a prerelease increment. It is not a repository prerelease identifier.
- Reject equal or decreasing targets. Do not use `pnpm version` or `npm version`: repository guidance records partial-edit failures around `workspace:*`. Edit only the selected manifest's `version` field.

Before any edit, show one block per package:

```text
Package: <full name>
Current: <manifest version>
Target:  <calculated version>
Release type: <stable or prerelease identifier>
npm dist-tag: <latest or next>
```

For multiple packages, also show dependency order and the files that will change. Do not give packages the same version unless their independently calculated intents happen to produce it or the user explicitly supplied each target.

## Inspect what will ship

For each package, find its newest reachable package tag with `git tag --merged HEAD --list "<package>@*" --sort=-version:refname`. Compare that tag to `HEAD` for the package path. If no package tag exists, report it as a first release from the current tree.

For "release the changed npm package", inspect changes for every managed path rather than every workspace. If zero or multiple managed packages changed, report the candidates and ask only when selection remains ambiguous. Do not automatically release a dependant merely because a dependency changed.

Internal dependencies use `workspace:*`. Keep those specifiers unchanged. pnpm rewrites them to package versions in the packed publication; historical version-only commits do not change `pnpm-lock.yaml`. If both a dependency and dependant are selected, bump both independently, commit them together if appropriate, then release and verify the dependency before the dependant. `@iracing-data/oauth-client` currently depends on `@iracing-data/oauth-schema`; derive this relationship from current manifests rather than relying on that example.

## Prepare safely

1. Read all applicable `AGENTS.md` files and `docs/RELEASING.md` again in case policy changed.
2. Inspect `git status --short --branch`. Preserve user changes. Stop if unrelated tracked or untracked changes make an isolated release commit unsafe; never stash, reset, clean, or overwrite them without explicit instruction.
3. Fetch current state with `git fetch origin main --tags --prune`. Require the work to be based on `origin/main`. The normal documented path is a reviewed branch/PR whose version bump is merged before tagging; do not bypass branch protection or required reviews.
4. Verify each proposed tag is absent locally and remotely:

   ```bash
   git rev-parse -q --verify "refs/tags/<tag>"
   git ls-remote --exit-code --tags origin "refs/tags/<tag>" "refs/tags/<tag>^{}"
   ```

   `git rev-parse` returns 1 for an absent local tag; `git ls-remote --exit-code` returns 2 when no remote ref matches. Confirm the command produced no matching ref, and distinguish absence from network/authentication errors.

5. Verify the target is absent from npm with `npm view "<package>@<target>" version`. A registry 404 means unpublished; a returned version is a hard conflict. Treat network, authentication, and registry errors as unknown and stop rather than assuming availability.
6. Update only each target manifest's version unless the release includes separately requested source/generated changes. A version-only bump does not require a lockfile edit; if the lockfile changes unexpectedly, inspect and explain it before continuing.
7. Install exactly as CI does when needed: `pnpm install --frozen-lockfile`.
8. For every target, run its declared test script when present, then run the CI-equivalent build:

   ```bash
   pnpm --filter "<package>" test
   pnpm --filter "<package>..." --fail-if-no-match build
   ```

   Do not run a nonexistent test script. For source changes, also require the repository's relevant lint/test checks or a successful CI run for the exact commit. Never bypass a failure.
9. Review `git diff --check`, the manifest diff, and `git status --short`. Stage explicit files only.
10. For a standalone one-package bump, use the recent convention `chore(<unscoped-name>): release <version>`. For several packages, use `chore(release): <name> <version> and <name> <version>`. If the bump is already part of a feature PR, keep it in that PR as documented rather than creating a redundant release commit.

After a prepare-only request, stop here and report the commit and validations. Do not push a release tag.

## Finalize a release

Do not tag until the prepared commit is on `main` and all required review/checks have passed.

1. Check out `main`, update from the remote without rewriting history, and fetch tags. Require a clean tree, `HEAD == origin/main`, and a successful CI result for that exact commit. If a direct push is disallowed, use the repository's PR path and wait for merge; do not tag the feature branch.
2. Re-read each version from the manifest and repeat the local tag, remote tag, and npm-version conflict checks immediately before tagging.
3. Create an annotated tag at `HEAD`:

   ```bash
   git tag -a "<package>@<version>" -m "Release <package> <version>"
   ```

4. Ensure the release commit is present on `origin/main` before publishing. Push only the one tag:

   ```bash
   git push origin "<package>@<version>"
   ```

   The tag push is the publish-triggering operation. Never force-push or move a release tag.
5. For multiple packages, process tags one at a time in dependency order. Watch the Release workflow and verify npm before pushing the next dependant tag:

   ```bash
   gh run list --workflow release.yml --event push --limit 20
   gh run watch <run-id> --exit-status
   npm view "<package>@<version>" version
   npm view "<package>" dist-tags --json
   gh release view "<package>@<version>"
   ```

   Match the workflow run by tag/head branch and commit SHA; do not assume the newest run is yours.

Do not run `npm publish` locally in the normal flow, manually add a dist-tag, or manually create the GitHub Release. Those are separate recovery actions and require a diagnosed reason plus explicit authorization to depart from the normal workflow.

## Failure handling

- Validation/build/test failure: stop before commit/tag, leave the worktree inspectable, and report the failing command. Fix only in-scope problems; never bypass the check.
- Existing local or remote tag: stop. Compare its peeled commit and package manifest. Never overwrite, delete, or force-update it.
- Existing npm version: stop. Do not republish; choose a new version only from new user intent.
- Release commit/PR push failure: no tag should be pushed. Keep the local commit and report the remote or branch-protection error.
- Tag push failure with no remote tag: keep the annotated local tag, diagnose authentication/network/ref rejection, and retry the same push only after the cause is resolved. If the remote tag appeared, treat publication as triggered.
- CI failure after tag push: first check the Actions logs, `npm view`, and the GitHub Release. Do not delete or retarget the tag. If nothing published and the failure is transient/configuration-only, rerun the failed job. If code or workflow changes are required, fix them on `main`; prefer a new version/tag. `workflow_dispatch` may recover an unpublished version from fixed `main` only with explicit fallback authorization and the correct `latest`/`next` choice; it will not create a GitHub Release.
- npm published but GitHub Release missing: do not rerun a successful publish. Rerun only the failed GitHub-release job when possible; otherwise report the partial state and request explicit authorization before manually creating a release.
- Ambiguous partial success: treat the registry as authoritative for whether the immutable package version exists. Never casually rewrite published history.

## Report outcomes

Keep these states separate: **completed locally**, **pushed/triggered**, and **confirmed published**. A successful tag push is not proof of npm publication.

Report one block per package:

```text
Released: <package>
Version: <old> → <new>
Git tag: <tag>
npm dist-tag: <latest|next>
Publish mechanism: <not triggered | tag pushed; CI pending | CI completed>
GitHub Release: <expected | created | not applicable | failed>
Status: <completed locally | pushed/triggered | confirmed published>
```

Include the validation commands/results, commit SHA, workflow URL when triggered, and any unverified step. For previews, label every item planned and make no release-success claim.
